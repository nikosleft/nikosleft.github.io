Voice-Enabled Pi Coding Agent

A local voice loop for a command-line coding agent. Hold a key, speak, and the agent answers out loud while a desktop avatar moves its mouth in time with the speech. Everything runs on one Windows PC, and the microphone is only open while you are recording.

01 / In plain language

I wanted to talk to my coding agent, not type at it.

The coding agent runs in a terminal. It can read my project, run commands, and write code, but every exchange happens through the keyboard and the screen. This project adds the two missing channels: it lets me speak a request out loud, and it reads the agent's answer back to me in a natural voice while a small character on the desktop moves its mouth.

Nothing is sent to a cloud service. Speech recognition, the language model, the speech synthesis and the avatar all run locally. The setup is assembled from three small TypeScript extensions to the agent plus a separate desktop overlay application, and the pieces talk to each other over loopback connections.

02 / The loop, piece by piece

Four steps, each with a job.

Speech in

Hold a key and talk.

A hotkey starts recording from the microphone. The clip is transcribed by a local faster-whisper model that stays loaded between utterances, so the first word comes back in about a third of a second. The microphone is never open unless that hotkey is held.

The agent turn

The transcript becomes the prompt.

The text is injected into the coding agent as a normal user message. Everything that follows is the agent doing its usual work: reading files, running tools, writing an answer. Nothing is sent to a hosted service.

Speech out

The final answer is spoken.

When the agent finishes, its answer is stripped of Markdown and code, sent to a local text-to-speech server, and the raw audio is streamed straight to the speakers. Starting to record again cancels playback immediately, so you can interrupt mid-sentence.

The avatar

A small window moves its mouth.

A transparent desktop overlay draws a Live2D character. It receives the agent state and the audio envelope over a local WebSocket, so the mouth opens with the speech and a listening or thinking pose appears at the right moment.

03 / Engineering details

The interesting part is the timing.

The input extension owns the microphone for exactly as long as it is needed. It records with ffmpeg, watches the audio level to find the end of a sentence, and sends the clip to a small Python server that keeps faster-whisper loaded in memory. That server answers over newline-delimited JSON on standard input and output, which avoids paying the model load cost on every utterance.

The speech extension listens for the agent's final message, strips formatting, and posts the text to a local text-to-speech HTTP API. The response is raw 16-bit 24 kHz PCM, not a file: it is piped into ffplay as it arrives, so playback starts before synthesis has finished. When a recording starts, the extension fires an event that stops the player immediately, which is what makes interrupting the agent feel natural.

The avatar needed audio analysis rather than a guess. A small library cuts the PCM stream into 20 millisecond frames, computes the RMS level to drive mouth opening, and uses a zero crossing rate as a cheap brightness signal. Those frames are stamped on a sample clock, so the mouth follows what is being played rather than when a network chunk happened to arrive. A dedicated lip-sync scheduler in the overlay interpolates between frames with different attack and release rates, then writes the Live2D mouth parameter every render frame.

The overlay is an Electron application: a transparent, frameless, always on top window that stays click-through so it never blocks the terminal. It hosts a small HTTP server for model assets and a WebSocket server for state, accepts one instance only to avoid competing for the GPU, and exposes a tray menu and global shortcuts. State priority is explicit: listening beats speaking, speaking beats tool execution, and idle is the fallback.

  • Transport: HTTP for synthesis, loopback WebSocket for avatar state, newline-delimited JSON over stdio for transcription, raw PCM over a pipe for playback.
  • Interruption: a barge-in event cancels speech the moment recording starts, and the avatar drops out of its speaking pose on the same signal.
  • Engine choice: the speech extension switches between two local engines, one GPU GGUF server and one CPU ONNX server, by configuration rather than code changes.
  • Failure handling: playback falls back to a buffered WAV player when the streaming player is unavailable, and log lines are best effort so diagnostics never break speech.

04 / Controls and animations

It has a face, a voice, and a control panel.

The character is not decoration. Every state in the loop is visible on her: listening, thinking while the model works, a tool pose while a command runs, and speech that drives her mouth in real time. The same states are exposed as commands, because a demo is only convincing if you can drive it.

A floating pill above her head carries the controls that matter mid-sentence: mute, stop, volume and speed. A tray icon gives show, hide and quit. Global shortcuts toggle interactive mode, show or hide the overlay, and quit it. None of it takes focus away from the terminal, because the window is click-through until you ask otherwise.

Agent commands

  • /companion on starts speech and the avatar for the session
  • /breeze voice and /breeze provider switch engine or voice
  • /voice mic and /voice model choose input device and model
  • /live2d interactive, /live2d customize, /live2d emote

Live reactions

  • Listening pose while the microphone is open
  • Thinking and tool poses while the agent works
  • Mouth driven by the audio envelope while speaking
  • Error face on a failed tool call, a small celebration on a clean one

Ambient detail

  • Attention badge when the agent is waiting on you
  • Streak halo after six clean tool calls
  • Context ring around the pill, tool bubble above her head
  • Idle habits every forty to a hundred seconds

05 / The stack

Four languages, four transports, one loop.

Extensions

TypeScript on the agent's extension API. Three modules, about 2,700 lines, sharing an event bus for speech start, speech end, audio level and barge-in.

Speech input

ffmpeg for capture, a Python server holding faster-whisper in memory, newline-delimited JSON over stdio, and level-based end-of-speech detection.

Speech output

Two interchangeable local engines: a GGUF model on the Vulkan backend for quality, or a small ONNX model on the CPU to keep the GPU free.

Audio path

Raw 16-bit 24 kHz PCM streamed from the synthesis API into ffplay, with a buffered WAV fallback when the streaming player is unavailable.

Animation

An Electron window running Live2D Cubism, a 20 ms sample-clock envelope for mouth and brightness, and an expression and motion layer on top.

Transport

HTTP for synthesis, a loopback WebSocket for avatar state, stdio for transcription, and pipes for playback. Everything bound to 127.0.0.1.

System glue

Windows Core Audio through PowerShell for per-application volume, so the slider changes level mid-sentence instead of restarting playback.

State machine

Explicit priority: listening over speaking, speaking over tool use, tool use over idle, with barge-in able to pre-empt any of them.

06 / What this is not

Personal tooling, with honest limits.

The speech models are third party. I integrated them, chose the engines, and wrote the orchestration, the streaming and the timing code; I did not train a speech model. The mouth animation is an amplitude envelope, not phoneme or viseme tracking, so it reads as convincing movement rather than accurate lip reading.

This is a single-user setup on one machine, not a deployed service. Every connection binds to loopback, there is no authentication layer, and the pieces assume a Windows desktop with a GPU available. It is also not packaged for other people to install.
